# 提示词润色设计（任务 5）

> 2026-10-17 · 阶段 1–6 定稿，随本文件一并进入实现（阶段 7）。

## 1. 问题定义

**谁在什么场景下遇到什么问题？**

用户在输入框里写提示词时，常常一口气写下口语化、结构松散、缺少上下文的一段话（例如「帮我看看那个登录那块是不是有点问题，顺便改改」）。这类提示词交给 Agent 后：

- 目标不明确（「看看」到底是审查还是修复？）
- 缺少约束（改到什么程度、要不要跑测试）
- 关键信息遗漏（哪个文件、哪个环境）

用户自己知道想干什么，但把意图转成清晰、结构化的提示词本身有成本。

**现状怎么凑合的？**

- 用户手动重写一遍，或先发给 Agent 让它「帮我理一下需求」再让 Agent 干活——多一轮往返。
- 部分用户干脆不润色，接受 Agent 理解偏差带来的返工。

**痛点归纳**：从「心里的意图」到「一条高质量提示词」之间有手工摩擦，且摩擦发生在最该顺滑的输入环节。

## 2. 概念模型

### 2.1 术语表

| 术语 | 定义 |
| --- | --- |
| 润色（polish） | 用一次 LLM 调用把当前输入框文本改写成更清晰、结构化的提示词，并回填 |
| 原文 / 润色稿 | 触发润色前的输入内容 / 润色后由模型返回的内容 |
| 回退 | 把输入框内容恢复为原文 |
| 一次性调用 | 不进入会话、不产生消息记录、不启用工具的单轮 chat completion |

### 2.2 能力边界

| 维度 | 润色（本特性） | 普通对话 |
| --- | --- | --- |
| 是否进入会话 | 否 | 是 |
| 是否产生消息记录 | 否 | 是 |
| 是否可用工具 | 否 | 是 |
| 输出去向 | 回填输入框，用户可编辑/回退 | 追加为会话消息 |
| 模型来源 | 当前首个启用的 provider（与 IM 相同口径） | 会话选定模型 |

## 3. 用户旅程

### 主流程：润色一段提示词

1. 用户在输入框写下一段口语化文本。
2. 输入框右侧出现「润色」按钮（语音按钮左侧）；文本为空或正在流式输出时不可用。
3. 点击后按钮进入加载态，输入框只读。
4. 主进程用当前 provider 模型把文本改写成结构化提示词。
5. 成功：输入框内容被替换为润色稿，同时弹出「已润色 · 撤销」入口，原文被保留。
6. 用户可直接发送润色稿，或点「撤销」恢复原文，或继续手工编辑。

### 异常流程

- **无可用模型**：点击后不进入加载态，提示「未配置可用模型」，输入框内容不变。
- **调用失败 / 超时**：提示失败原因，**保留原文**、不改写输入框，按钮恢复可用。
- **原文为空**：按钮保持禁用，无任何请求。
- **润色中用户切换会话 / 卸载组件**：请求结果丢弃，不写入任何草稿。
- **连续点击**：加载态期间按钮禁用，防止并发调用。

### 4.1 功能清单

| 编号 | 需求 | 优先级 |

| FR-P1 | 输入框右侧、语音按钮左侧提供「润色」按钮（大布局与紧凑布局均需） | P0 |

| FR-P5 | 无可用模型 / 调用失败时给出明确提示且不改动原文 | P0 |
| FR-P6 | 文本为空、禁用、流式输出、远程托管时不触发 | P0 |
| FR-P7 | 支持取消 / 卸载安全：请求完成前组件卸载或换会话则丢弃结果 | P1 |

### 4.2 不做清单

- 不做多轮润色对话（一次调用得一个结果）。
- 不做润色历史（仅保留最近一次原文用于撤销）。
- 不做「选择润色风格」等参数选项（先用一套通用指令）。
- 不改写会话消息，只作用于输入草稿。

## 5. 交互设计

### 5.1 按钮

- 图标：`SparklesIcon`（Heroicons outline）。
- 位置：工具栏按钮组中，`largeVoiceInputButton` **之前**；紧凑布局同理。
- 禁用条件：`disabled || voiceInputLocksEditing || isStreaming || !hasPromptText || isPolishing`。
- 加载态：图标替换为旋转指示，`aria-busy`，`title` 显示「润色中…」。
- 无模型可用时：按钮仍可见但点击后提示，不静默失败（区别于禁用，便于用户知晓原因）。

### 5.2 撤销入口

- 润色成功后，在输入框上方（附件预览同一区域）显示一条轻量提示条：`已润色 · 撤销`。
- 点击「撤销」恢复原文并清除提示条；用户开始编辑或发送后提示条自动消失。

### 5.3 状态设计

| 状态 | 表现 |
| --- | --- |
| 空 | 按钮禁用（无文本） |
| 加载 | 按钮旋转，输入框只读，发送按钮禁用 |
| 成功 | 回填内容 + 撤销提示条 |
| 无模型 | toast / 行内提示「未配置可用模型」 |
| 失败 | 行内提示错误摘要，原文保留 |

## 6. 架构设计

### 6.1 模块划分

| 模块 | 改动 |
| --- | --- |
| `src/shared/cowork/constants.ts` | 新增 IPC 频道常量 `CoworkPolisherChannels`（请求/响应） |
| `src/main/libs/promptPolisher.ts`（新增） | 纯逻辑：解析 LLM 配置 → 构造一次性 completion → 提取文本；可单测 |
| `src/main/main.ts` | 注册 IPC handler，注入 `getLLMConfig` 同款解析器；复用 `IMChatHandler` 的 provider 判定口径 |
| `src/main/preload.ts` | 暴露 `electron.cowork.polishPrompt({ text })` |
| `src/renderer/types/electron.d.ts` | 补类型 |
| `src/renderer/components/cowork/CoworkPromptInput.tsx` | 按钮、状态、撤销条、调用 |
| `src/renderer/services/i18n.ts` | 文案（中英） |

### 6.2 接口契约

```
// 主进程 handler
IPC: 'cowork:polish-prompt'
入参: { text: string }
返回:
  | { ok: true; text: string }        // 润色稿
  | { ok: false; reason: 'no-model' | 'empty' | 'failed'; message?: string }
```

- 入参 `text` 在主进程 trim 后为空 → 直接返回 `{ ok:false, reason:'empty' }`，不发请求。
- 润色指令（system prompt）固定；用户文本作为 user message。

### 6.3 模型解析

复用与 IM 相同的口径：读 `app_config`，取**首个 enabled 且有 apiKey 的 provider**，用其 `models[0].id`；否则回退 `app_config.api` / `model.defaultModel`。抽取为 main 内共享函数 `resolveOneShotLlmConfig(sqliteStore)`，同时替换 `imGatewayManager.initialize` 中内联的同类逻辑，避免两份口径漂移。

- provider 为 anthropic 或其模型以 `claude` 开头 → 走 `/v1/messages`。
- 其余 → OpenAI 兼容 `/chat/completions`（含 Gemini / OpenAI Responses 的既有判定，直接复用 `IMChatHandler` 的 URL 构造口径）。
- 超时：30s；`max_tokens` 上限 2048（润色输出远小于此）。

### 6.4 选型理由

- **不复用 OpenClaw 运行时**：润色不应产生会话/消息/工具调用副作用，且需要「当前 provider」而非会话模型。直接用 provider 端点最轻。
- **复用 IM 的 LLM 解析**：IM 已有"用首个启用 provider 做一次性调用"的成熟实现，抽出来共享比另写一份更稳。
